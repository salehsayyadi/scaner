# Scaner

اسکنر آی‌پی تمیز برای کانفیگ‌های VLESS (Xray). لینک یا کانفیگ خودتان را وارد می‌کنید، رنج آی‌پی‌ها را می‌دهید و برنامه آی‌پی‌هایی را که واقعاً وصل می‌شوند با پینگ، افت و سرعت پیدا می‌کند.

دانلود: [صفحه Releases](https://github.com/salehsayyadi/scaner/releases/latest)


## فایل‌های هر نسخه

| فایل | توضیح |
|---|---|
| `Scaner-Setup-<نسخه>.exe` | نصب‌کننده ویندوز (پیشنهادی). میانبر در منوی استارت و دسکتاپ می‌سازد. |
| `Scaner-<نسخه>-windows-amd64-PORTABLE.exe` | نسخه پورتابل ویندوز، بدون نصب. فقط اجرایش کنید. |
| `Scaner-cli-<نسخه>-windows-amd64.exe` | نسخه خط فرمان (CLI/TUI) برای اجرا در cmd یا PowerShell. |
| `Scaner-<نسخه>-android.apk` | نسخه اندروید، بدون نیاز به روت. |
| `Scaner-<نسخه>-source.zip` | سورس کامل همان نسخه. |
| `SHA256SUMS.txt` | هش فایل‌ها برای اطمینان از سالم بودن دانلود. |

تنظیمات و نتایج در پوشه اطلاعات برنامه ذخیره می‌شوند، نه کنار فایل اجرایی.

## راهنمای ریست و تشخیص اتصال

- **ریست کانفیگ:** فقط آدرس، UUID، ‏Flow، TLS/Reality و جزئیات انتقال را پاک می‌کند. رنج‌ها و تنظیمات اسکن حفظ می‌شوند.
- **ریست اسکن:** اهداف، حالت اسکن، نمونه‌برداری و تنظیمات `scan` را به پیش‌فرض برمی‌گرداند. کانفیگ، فرگمنت و فایل‌های نتایج دست‌نخورده‌اند.
- **ریست فقط تنظیمات:** تمام گزینه‌های بخش Settings یعنی اندازه‌گیری، فرگمنت، خروجی، Xray، دیباگ، زبان و تم را به پیش‌فرض برمی‌گرداند؛ کانفیگ، اهداف و تاریخچه پاک نمی‌شوند. پیش‌فرض زبان انگلیسی و تم مطابق سیستم است.
- **ریست نتایج:** فقط جدول فعلی، انتخاب ردیف و فیلترهای نمایش را پاک می‌کند؛ فایل‌های ذخیره‌شده حذف نمی‌شوند.
- **ریست تاریخچه/گزارش:** پس از تأیید، به‌ترتیب فایل‌های اسکن تولیدشده در پوشه خروجی فعلی، یا لاگ و فایل دیباگ را حذف می‌کند.
- **تمام داده‌های برنامه:** کانفیگ، اهداف، تنظیمات، نتایج نمایشی، گزارش و ترجیحات را ریست می‌کند. فایل‌های تولیدشده با نام استاندارد برنامه در پوشه خروجی فعلی و پیش‌فرض حذف می‌شوند. پوشه خروجی به‌صورت کامل حذف نمی‌شود؛ اسناد نامرتبط، خروجی‌های دستی و پوشه‌های خروجی قدیمی دیگر حذف نمی‌شوند.

### اگر یک آی‌پی در v2rayN وصل است ولی در اسکنر رد می‌شود

1. همان لینک را اعمال کنید و بدون تغییر جزئیات، از «تست کانفیگ» استفاده کنید. این تست فقط اتصال سرور اصلی به **آدرس تست تنظیم‌شده** را بررسی می‌کند؛ شکست یک مقصد وب به‌تنهایی اثبات خرابی کل کانفیگ نیست.
2. برای مقایسه، هر دو برنامه را روی همان اینترنت و با وضعیت یکسان VPN/پراکسی سیستم آزمایش کنید. در تست اسکنر، فرگمنت و Mux را فقط اگر در اتصال مرجع هم فعال‌اند روشن کنید.
3. از «لیست آی‌پی» استفاده کنید و همان آی‌پی را دقیق وارد کنید؛ در حالت رنج با نمونه‌برداری، ممکن است اصلاً آن آی‌پی انتخاب نشود.
4. برای تشخیص اولیه، تعداد ورکر را ۱، Timeout را ۱۵ تا ۲۰ ثانیه، Maximum latency را ۰، Maximum loss را ۰ و حداقل آپلود/دانلود را ۰ بگذارید. تست سرعت را خاموش کنید. سپس محدودیت‌ها را مرحله‌به‌مرحله اضافه کنید.
5. گزینه «فقط سالم‌ها» را خاموش کنید و ردیف ناموفق را انتخاب کنید. «خارج از معیار» یعنی درخواست از طریق Xray موفق شده ولی حد کیفیت شما را رد کرده؛ این با شکست احراز هویت/اتصال فرق دارد. در «جزئیات» یا گزارش، خطای دقیق را ببینید.
6. اگر کانفیگ از قابلیت جدیدتری استفاده می‌کند، توجه کنید هسته فعلی پروژه `xray-core v1.8.24` است. این نسخه ادعای پشتیبانی از همه قابلیت‌های کلاینت‌های جدید را ندارد. تغییرات ناشناخته مثل VLESS encryption جدید پشتیبانی نمی‌شوند؛ موارد شناسایی‌شده با خطای روشن رد می‌شوند، نه تبدیل به اتصال دیگری.

## استفاده از «منتخب رنج‌ها»

۱. اسکن را اجرا کنید یا یک نتیجهٔ ذخیره‌شده را باز کنید. این بخش **نتایج موجود را نمایش می‌دهد**؛ اسکن مجدد نمی‌کند و تنظیمات اسکن را تغییر نمی‌دهد.
۲. تب «منتخب رنج‌ها» (در موبایل «رنج‌ها») را باز کنید. در موبایل دکمه بالای صفحه فیلترها را باز می‌کند.
۳. «انتخاب رنج‌ها» را بزنید؛ جست‌وجو کنید و مثلاً از ۴۰ رنج، ۳ رنج را تیک بزنید. جست‌وجو انتخاب‌های پنهان را پاک نمی‌کند. سپس «اعمال» را بزنید. انتخاب هیچ رنجی یعنی نمایش هیچ نتیجه‌ای.
۴. «تعداد از هر رنج» را مثلاً ۲ بگذارید (۱ تا ۱۰۰۰). حداکثر ۶ آی‌پی خواهید دید: دو مورد در هر یک از سه گروه، با خط جداکننده. رنجی که کمتر از دو نتیجهٔ واجد شرایط دارد، فقط همان تعداد را نشان می‌دهد.
۵. معیار را انتخاب کنید: **پینگ** صعودی، **دانلود/آپلود** نزولی. **کیفیت** ابتدا سطح افت بسته در بازه‌های ۱۰درصدی کمتر، سپس پینگ کمتر و در تساوی افت دقیق و جیتر کمتر است. IP معیار نهایی برای ترتیب پایدار است.

فقط نتایج موفق واجد شرایط‌اند؛ رتبه‌بندی دانلود/آپلود فقط اندازه‌گیری‌های انجام‌شده را حساب می‌کند. علامت `—` یعنی اندازه‌گیری نشده، نه سرعت صفر. برای رتبه‌بندی سرعت، تست مربوطه را پیش از اسکن در تنظیمات روشن کنید. هر آی‌پی در یک گروه تکراری نمایش داده نمی‌شود.

«کپی آی‌پی‌های نمایشی»، «کپی گروه‌بندی» و خروجی‌ها فقط همین انتخاب‌های محدودشده را شامل می‌شوند، نه همه نتایج. دکمه کنار عنوان هر رنج فقط آی‌پی‌های نمایشی همان گروه را کپی می‌کند. «جزئیات» معیارهای کامل هر آی‌پی را باز می‌کند. در موبایل خروجی‌ها، کپی گروه‌بندی و ریست در «عملیات بیشتر» هستند.

رنج مبدأ در نتیجه‌های جدید ذخیره می‌شود و تغییر بعدی متن رنج‌های اسکن آن را عوض نمی‌کند. در رنج‌های همپوشان، مبدأ همان اولین رنج مطابق در ساخت اهداف است. برای فایل قدیمی بدون ستون Range، در صورت وجود رنج‌های فعلی از آن‌ها کمک گرفته می‌شود؛ موارد بدون انتساب در گروه «آی‌پی‌های تکی / بدون رنج» می‌آیند.

## نسخه 6.6.4 — بتای خصوصی، هنوز عمومی نشده

نسخه پایدار عمومی فعلی **5.6.4** است. نسخه **6.6.4-beta** قابلیت جدید Cloudflare DNS دارد و هنوز عمومی نشده است. کد و فایل اجرایی بتا در [مخزن خصوصی scaner-beta](https://github.com/salehsayyadi/scaner-beta) و [Release خصوصی 6.6.4](https://github.com/salehsayyadi/scaner-beta/releases/tag/v6.6.4) قرار می‌گیرند. دسترسی فقط با ورود به حساب مالک یا حساب همکار دعوت‌شده و پذیرفتن دعوت ممکن است؛ دیگران معمولاً خطای 404 می‌بینند. خصوصی بودن مانع بازنشر فایل توسط کسی که قبلاً دانلود کرده نیست.

Release عمومی این نسخه **فقط معرفی** است و فایل اجرایی یا سورس بتا ندارد. فایل‌های خودکار Source code در Release عمومی فقط تصویر سورس عمومی پایدارند، نه کد بتای خصوصی. برای درخواست دسترسی، نام کاربری GitHub را به مالک بدهید؛ هیچ حسابی خودکار دعوت نمی‌شود.

### تغییر DNS در Cloudflare از منتخب رنج‌ها

1. اسکن را تمام کنید. در «منتخب رنج‌ها»، رنج‌های موردنظر، تعداد آی‌پی هر رنج و معیار پینگ، دانلود، آپلود یا کیفیت را انتخاب کنید. فقط نتایج موفق واجد شرایط‌اند؛ سرعت اندازه‌گیری‌نشده صفر نیست و وارد رتبه‌بندی سرعت نمی‌شود.
2. «Cloudflare DNS» را باز کنید (موبایل: عملیات بیشتر). برنامه **همان آی‌پی‌های نمایش‌داده‌شده در لحظه بازکردن فرم** را ثبت می‌کند؛ هنگام تأیید دوباره رتبه‌بندی یا اسکن نمی‌کند.
3. گزینه فعال‌سازی تغییر رکوردها را روشن کنید؛ به‌صورت پیش‌فرض خاموش است. دامنه یا دامنه پایه مورد استفاده و توکن را وارد کنید. دامنه باید بدون https، پورت یا مسیر باشد؛ دامنه بین‌المللی را به شکل Punycode بنویسید.
4. برای هر رنج، نام رکوردها را به ترتیب رتبه وارد کنید؛ جداکننده کاما، ویرگول فارسی، فاصله یا خط جدید است. نام کوتاه مثل `v4-0` به دامنه اضافه می‌شود؛ نام کامل باید زیر همان دامنه باشد. برای زیردامنه چندبخشی، نام کامل را وارد کنید. `@` یعنی خود دامنه.
5. «پیش‌نمایش تغییرات» فقط اطلاعات را می‌خواند و چیزی را تغییر نمی‌دهد. نام رکورد، IP قبلی و IP جدید را بررسی کنید؛ فقط با تأیید نهایی تغییر اعمال می‌شود.

نمونه برای شش رنج ثابت: نام‌ها نمونه‌اند؛ CIDRهای واقعی خودتان را انتخاب کنید.

| ترتیب رنج انتخاب‌شده | نام دو رکورد به ترتیب بهترین نتیجه |
|---|---|
| رنج اول | `v4-0, v4-1` |
| رنج دوم | `v4-2, v4-3` |
| رنج سوم | `v4-4, v4-5` |
| رنج چهارم | `v4-6, v4-7` |
| رنج پنجم | `v4-8, v4-9` |
| رنج ششم | `v4-10, v4-11` |

مثلاً برای دامنه `saleh.example.com`، نتیجه اول رنج اول به `v4-0.saleh.example.com` و نتیجه دوم به `v4-1.saleh.example.com` می‌رود. ارتباط هر رنج با نام‌ها مستقل ذخیره می‌شود، نه بر اساس جابه‌جایی جای رنج‌ها در صفحه. تعداد نام‌ها می‌تواند بیشتر از دو باشد؛ نام اول به رتبه اول همان رنج مربوط است. اگر نتیجه کافی نباشد، رکورد متناظر با رتبه خالی تغییر نمی‌کند.

### ساخت و نگهداری توکن

در Cloudflare → My Profile → API Tokens یک توکن سفارشی بسازید: مجوزهای **Zone → Zone → Read** و **Zone → DNS → Edit**، با Zone Resources محدود به **فقط Zone موردنظر**. از Global API Key استفاده نکنید. برنامه Zone ID را با خواندن دامنه و والدهای آن پیدا می‌کند؛ نیازی به واردکردن دستی Zone ID نیست.

توکن فقط در حافظه فرم/درخواست است و در تنظیمات، Session، خروجی یا لاگ ذخیره نمی‌شود؛ پس از بستن فرم یا پایان اعمال، ورودی پاک می‌شود. دامنه و نگاشت نام‌ها اطلاعات محرمانه محسوب نشده و ذخیره می‌شوند. API فقط به میزبان ثابت Cloudflare ارسال می‌شود و تغییر مسیر HTTP پذیرفته نمی‌شود. توکن را در Issue، README یا مخزن قرار ندهید.

### محدودیت‌ها و ایمنی بتا

- فقط **رکورد موجود** با نام و نوع دقیق پشتیبانی می‌شود: IPv4 → A، IPv6 → AAAA. رکورد گمشده یا چند رکورد هم‌نام و هم‌نوع باعث توقف پیش‌نمایش می‌شود. ساختن و حذف‌کردن رکورد، CNAME و ویرایش چند Zone هم‌زمان انجام نمی‌شود. نام تکراری در نگاشت رنج‌ها مجاز نیست.
- فقط مقدار IP با PATCH تغییر می‌کند؛ TTL و وضعیت DNS only/Proxied حفظ می‌شوند، نه اینکه خودکار خاموش یا روشن شوند.
- پیش از ویرایش هر رکورد، وضعیت آن دوباره خوانده می‌شود؛ اگر از زمان پیش‌نمایش تغییر کرده باشد، ویرایش آن کنار گذاشته می‌شود. این بررسی قفل تراکنشی Cloudflare نیست و رقابت هم‌زمان را کاملاً حذف نمی‌کند.
- عملیات چندرکوردی **اتمی نیست**: ممکن است چند رکورد موفق و چند رکورد ناموفق باشند؛ بازگردانی خودکار انجام نمی‌شود. خطای شبکه پس از ارسال درخواست می‌تواند نتیجه نامعلوم بدهد؛ قبل از تکرار، وضعیت را در Cloudflare بازخوانی کنید. بستن فرم درخواست‌های بعدی را لغو می‌کند ولی تغییر قبلاً ارسال‌شده لزوماً برنمی‌گردد.
- توکن بدون مجوز، رکورد حذف‌شده، محدودیت نرخ یا اختلال شبکه خطا می‌دهد؛ تلاش خودکار نامحدود وجود ندارد. یکسان‌بودن IP بدون تغییر گزارش می‌شود. اثر DNS ممکن است تا پایان TTL و کش کلاینت فوری دیده نشود.
- این قابلیت فقط با اقدام دستی اجرا می‌شود؛ زمان‌بندی، تغییر خودکار پس از اسکن یا تضمین دسترسی به IP وجود ندارد. API مدیریتی Cloudflare از مسیر معمول سیستم استفاده می‌کند؛ انتخاب کارت شبکه در Settings مخصوص ترافیک تست است.
- آزمون‌های خودکار API شبیه‌سازی‌شده شامل ۱۲ رکورد، ترتیب و snapshot نتایج، کمبود نتیجه، خطای جزئی و رکورد تغییرکرده است. **تست زنده با توکن یا DNS واقعی کاربر انجام نشده**؛ اول روی رکوردهای آزمایشی امتحان کنید.
- بتا نصب و داده مستقل دارد: Windows در `ScanerBeta` و شناسه برنامه `com.piyazche.scaner.beta`. تنظیمات پایدار خودکار منتقل نمی‌شوند. نسخه Android بتا در نبود کلید خصوصی انتشار با کلید تست امضا می‌شود؛ برای انتشار تولیدی مناسب نیست. فایل‌های ویندوز امضای Authenticode ندارند.

### حذف پیش‌نمایش وب در 6.6.4

پیش‌نمایش وب کنار گذاشته شده است: پوشه و workflow وب، لینک فعال Pages و فایل‌های HTML پیش‌نمایش Releaseهای قبلی حذف می‌شوند. نسخه جدید فقط برنامه بومی است و پنل اسکن وب ارائه نمی‌کند. سوابق تاریخی Git ممکن است همچنان شامل فایل‌های قدیمی باشند؛ تاریخچه انتشارهای بومی بازنویسی نمی‌شود.

## راهنمای کامل گزینه‌های Settings

### اینترنت مورد استفاده برای تست — اولین کارت تنظیمات

| گزینه | کارکرد دقیق |
|---|---|
| خودکار (مسیر سیستم) | رفتار قبلی؛ مسیر خروج را ویندوز/سیستم‌عامل انتخاب می‌کند. اگر VPN در مسیر پیش‌فرض یا TUN باشد، تست هم ممکن است از VPN برود. این حالت هیچ ادعایی درباره اینترنت خام ندارد. |
| کارت شبکهٔ مشخص | Wi-Fi یا Ethernet متصل به اینترنت مورد نظر را انتخاب کنید، نه آداپتور مجازی VPN. برنامه نام/شناسه کارت را نشان می‌دهد و آدرس‌های آن را در توضیحات می‌آورد؛ خودش حدس نمی‌زند کدام کارت VPN است. |
| به‌روزرسانی فهرست کارت‌ها | بعد از وصل/قطع وای‌فای، هات‌اسپات، کابل یا VPN دوباره فهرست کارت‌های فعال را می‌خواند. کارت ذخیره‌شدهٔ غایب با «در دسترس نیست» باقی می‌ماند، نه اینکه انتخاب به خودکار تغییر کند. |

**روش استفاده در ویندوز هنگام اتصال VPN:** اسکن و بهینه‌سازی را متوقف کنید؛ در Settings اولین کارت را باز کنید؛ کارت فیزیکی اینترنت مطلوب مثل Wi-Fi یا Ethernet را انتخاب کنید و «تست کانفیگ» را بزنید. تغییر مسیر فقط برای تست‌های بعدی است. برای تعویض اینترنت، اجرای فعال باید تمام شود. انتخاب دستی از `IP_UNICAST_IF` برای IPv4 و `IPV6_UNICAST_IF` برای IPv6 استفاده می‌کند؛ هیچ route، metric، پروکسی ویندوز یا تنظیم VPN را تغییر نمی‌دهد.

این انتخاب شامل اتصال خروجی Xray (و فرگمنت)، تست اتصال کانفیگ، پینگ/دانلود/آپلود داخل همان تونل، پیش‌تست TCP و بهینه‌ساز است. در حالت دسترسی‌پذیری، انتخاب دستی از TCP روی پورت‌های 443/80 استفاده می‌کند؛ آن را پینگ ICMP حساب نکنید. اگر اتصال کارت یا مجوز بستن سوکت به آن از دست برود، تست خطا می‌دهد و روی اینترنت دیگری ادامه نمی‌دهد.

**محدودیت مهم VPN:** کیل‌سوئیچ، WFP/firewall، فیلتر سطح سیستم، هدایت اجباری یا نبود مسیر مستقیم ممکن است اتصال کارت انتخابی را هم مسدود یا رهگیری کند. این قابلیت تضمین دورزدن VPN نیست و آی‌پی عمومی مسیر را خودکار تأیید نمی‌کند. DNS سرورهای سیستم روی سوکت مقید استفاده می‌شوند؛ DNS فقط‌در‌دسترسِ VPN یا DNS محلی ممکن است پاسخ ندهد. اسکن مقصد عددی کمتر به DNS سرور کانفیگ وابسته است، اما نام میزبان مقصد تست هم ممکن است به DNS نیاز داشته باشد. برای مقایسه قطعی، در صورت امکان یک بار با VPN خاموش هم تست کنید؛ لازم نیست و نباید تنظیمات امنیتی VPN را صرفاً برای این برنامه تضعیف کنید.

در لینوکس دسکتاپ از `SO_BINDTODEVICE` استفاده می‌شود و بسته به مجوز سیستم ممکن است اجازه لازم داشته باشد؛ خطای مجوز به کاربر برگردانده می‌شود. اندروید/پلتفرم‌های دیگر فعلاً فقط مسیر خودکار دارند؛ انتخاب دستی غیرفعال است. حالت دستی برای ترنسپورت‌های TCP/HTTP2 است؛ ALPN برابر `h3`/QUIC صریحاً با خطا متوقف می‌شود تا مسیر نامطمئن به‌جای مسیر انتخابی استفاده نشود.

نام کارت در خروجی جدید با `Test interface` / `test_interface` ذخیره می‌شود؛ مقدار خالی یعنی خودکار. نام شبکه روی دستگاه دیگر ممکن است فرق داشته باشد؛ اگر فایل تنظیمات کامل منتقل کردید، دوباره کارت مناسب همان دستگاه را انتخاب کنید. ورود لینک VLESS انتخاب اینترنت را حفظ می‌کند؛ ورود JSON کامل برنامه مقادیر همان فایل را می‌آورد.

واحدها مهم‌اند: تأخیر و فاصلهٔ فرگمنت بر حسب **میلی‌ثانیه**، Timeout بر حسب **ثانیه**، اندازه داده بر حسب **بایت** و سرعت بر حسب **مگابیت بر ثانیه (Mbps)** است. این تنظیمات نتیجه را عوض می‌کنند؛ «ردشدن بر اساس کیفیت» لزوماً به معنی خراب‌بودن کانفیگ نیست.

### Scan & quality measurements — اسکن و اندازه‌گیری کیفیت

| گزینه / کلید | دقیقاً چه کاری می‌کند؟ | راهنمای انتخاب |
|---|---|---|
| Threads / `threads` | تعداد آی‌پی‌هایی که هم‌زمان تست می‌شوند؛ هرکدام هسته و اتصال خودش را دارد. | پیش‌فرض ۸؛ برای اینترنت ضعیف یا تشخیص مشکل، ۱ تا ۴. تعداد زیاد می‌تواند خودِ تست را دچار رقابت پهنای‌باند و شکست کند. |
| Timeout / `timeout` | سقف انتظار هر درخواست تست و اتصال سرد. بودجه کل اسکن یا کل مراحل یک آی‌پی نیست؛ تکرار، نمونه‌های پینگ و تست‌های دیگر می‌توانند زمان کل را بیشتر کنند. | پیش‌فرض ۱۰ ثانیه؛ برای کانفیگ کند/فرگمنت ۱۵ تا ۲۰. تست سرعت محدودیت جداگانهٔ ۱۰ تا ۱۵ ثانیه‌ای دارد. |
| Test URL / `testUrl` | مقصد HTTP/HTTPS که **از داخل تونل** درخواست می‌شود؛ برای تست کانفیگ، پینگ، اتصال سرد و تست افت استفاده می‌شود. | پیش‌فرض `https://www.gstatic.com/generate_204`. یک مقصد سبک و قابل‌دسترسی از سرور انتخاب کنید. پاسخ ۲۰۰ تا ۳۹۹ موفق محسوب می‌شود؛ ریدایرکت دنبال نمی‌شود. |
| Maximum latency / `maxLatency` | حداکثر تأخیر قابل قبول بر حسب ms؛ در اسکن پراکسی بر حداقل تأخیر اندازه‌گیری‌شده اعمال می‌شود، نه کل زمان شروع هسته. برای نمونه‌های گرم هم بودجه زمانی ایجاد می‌کند. در حالت دسترسی‌پذیری نیز فیلتر تأخیر است. | پیش‌فرض ۲۵۰۰؛ صفر یعنی این فیلتر خاموش. تست مستقل کانفیگ این فیلتر را اعمال نمی‌کند. |
| Retries / `retries` | تعداد کل تلاش‌های تست هر آی‌پی، نه تعداد اضافه پس از تلاش اول. با اولین موفقیت متوقف می‌شود. پیش‌تست TCP حداکثر دو تلاش کمکی دارد. | پیش‌فرض ۲. در اسکن پراکسی صفر/منفی به حداقل یک تلاش تبدیل می‌شود؛ در حالت دسترسی‌پذیری صفر/منفی به ۳ تلاش تبدیل می‌شود. |
| Maximum IPs / `maxIPs` | سقف کل آی‌پی‌های صف پس از ساخت اهداف. | صفر یعنی بدون سقف تنظیم‌شده؛ محدودیت ایمنی تولید اهداف همچنان برقرار است. |
| Shuffle / `shuffle` | ترتیب اهداف حالت رنج را تصادفی می‌کند. | لیست آی‌پی صریح ترتیب ورودی را حفظ می‌کند؛ برای پیدا کردن سریع‌تر نمونه‌های پراکنده از رنج‌ها روشن بماند. |
| IPs per subnet / `sampleSize` | تعداد آی‌پی انتخاب‌شده از هر رنج؛ همان گزینه «آی‌پی از هر رنج» در تب اسکن است. | پیش‌فرض ۱۰۰؛ صفر یعنی همه آدرس‌ها تا سقف ایمنی. در حالت «لیست آی‌پی» نمونه‌برداری انجام نمی‌شود. |
| TCP pre-check / `tcpPrecheck` | پیش از Xray یک اتصال TCP مستقل به آی‌پی و پورت کانفیگ می‌زند و زمان آن را ثبت می‌کند؛ موفقیت این مرحله به معنی سالم‌بودن VLESS نیست. از 4.5.4 شکست آن به‌تنهایی آی‌پی را حذف نمی‌کند. | اختیاری و صرفاً کمکی؛ در مسیرهای QUIC/h3 اجرا نمی‌شود. بودجه آن حدود ۱ تا ۵ ثانیه و حداکثر Timeout است. |
| Realistic warm ping / `realisticPing` | ابتدا تونل را گرم می‌کند و سپس درخواست‌های تکراری با امکان استفاده مجدد از اتصال می‌فرستد. تأخیر گزارش‌شده حداقل نمونه‌های معتبر است؛ میانگین و jitter جدا ثبت می‌شوند. | پیش‌فرض روشن. این «زمان پاسخ درخواست وب داخل تونل» است، نه پینگ خام ICMP. |
| TLS handshake test / `handshakeTest` | مرحله اتصال سرد را اندازه می‌گیرد؛ در عمل یک درخواست کامل به Test URL از داخل تونل است. اگر URL از نوع HTTPS باشد، TLS مقصد هم در زمان آن هست. | پیش‌فرض روشن؛ اگر این گزینه یا Realistic ping روشن باشد مرحله گرم‌کردن/اتصال سرد انجام می‌شود. |
| Ping samples / `pingSamples` | تعداد درخواست‌های نمونه برای حداقل، میانگین و jitter. | پیش‌فرض ۴؛ بیشترکردن، زمان و داده بیشتری مصرف می‌کند. صفر/منفی به ۴ تبدیل می‌شود. |
| Packet-loss test / `lossTest` | چند درخواست هم‌زمان با اتصال تازه می‌فرستد تا قابلیت برقراری اتصال جدید را بسنجد. | این عدد **درصد شکست درخواست/اتصال** است، نه اندازه‌گیری افت بسته در لایه IP. پیش‌فرض روشن. |
| Loss samples / `lossSamples` | تعداد اتصال‌های تازه برای تست افت؛ هرکدام تا Timeout فرصت دارد. | پیش‌فرض ۶؛ تعداد بیشتر دقت نمونه‌برداری و بار تست را افزایش می‌دهد. صفر/منفی به ۶ تبدیل می‌شود. |
| Maximum loss / `maxLoss` | آی‌پی متصل را اگر درصد شکست درخواست‌های تست افت از این مقدار بیشتر باشد، از نتایج خوب کنار می‌گذارد. | صفر یعنی بدون فیلتر. برای معنی‌داربودن این گزینه، Loss test را روشن کنید. |
| Upload test / `uploadTest` | یک POST با داده مشخص از داخل تونل ارسال و سرعت را اندازه می‌گیرد. شکست تست سرعت جداگانه ثبت می‌شود. | پیش‌فرض خاموش. اگر حداقل آپلود صفر باشد، شکست تست سرعت به‌تنهایی اتصال را رد نمی‌کند. |
| Upload URL / `uploadUrl` | مقصدی که POST تست آپلود را می‌پذیرد. | پیش‌فرض `https://speed.cloudflare.com/__up`؛ مقصد باید واقعاً ارسال داده را قبول کند. |
| Upload payload / `uploadBytes` | تعداد بایت ارسالی در هر تست آپلود. | پیش‌فرض ۲۶۲۱۴۴ بایت، یعنی ۲۵۶ KiB. بزرگ‌تر دقیق‌تر ولی پرمصرف‌تر است. صفر/منفی هنگام اعتبارسنجی به ۱۰۰۰۰۰۰ تبدیل می‌شود. |
| Minimum upload / `minUpload` | حداقل Mbps برای پذیرفتن آی‌پی، فقط وقتی Upload test روشن است. | صفر یعنی بدون فیلتر سرعت آپلود. |
| Download test / `downloadTest` | دریافت داده از داخل تونل و محاسبه سرعت؛ نتیجه و خطای آن جدا ثبت می‌شود. | پیش‌فرض خاموش؛ می‌تواند اینترنت زیادی مصرف کند. |
| Download URL / `downloadUrl` | مقصد GET تست دانلود. برای این درخواست پارامتر `bytes`، اگر موجود نباشد، با مقدار Download payload اضافه می‌شود. | پیش‌فرض `https://speed.cloudflare.com/__down`؛ در مقصدهای دیگر باید رفتار سرور را بررسی کنید. |
| Download payload / `downloadBytes` | حجم درخواست‌شده در پارامتر `bytes`؛ سرور باید این پارامتر را رعایت کند. برنامه بدنهٔ پاسخ واقعی را می‌خواند، بنابراین این مقدار سقف سخت دانلود برای سرور دلخواه نیست. | پیش‌فرض ۱۰۴۸۵۷۶ بایت، یعنی ۱ MiB. صفر/منفی هنگام اعتبارسنجی به ۲۰۰۰۰۰۰ تبدیل می‌شود. |
| Minimum download / `minDownload` | حداقل Mbps برای پذیرش آی‌پی، فقط وقتی Download test روشن است. | صفر یعنی بدون فیلتر سرعت دانلود. |

**نکتهٔ زمان‌بندی:** نمونه‌های گرم از Maximum latency (حداقل داخلی ۳۰۰ms و حداکثر Timeout) استفاده می‌کنند؛ اتصال سرد و نمونه‌های افت از Timeout کامل استفاده می‌کنند. تست‌های سرعت برای هر درخواست بودجه‌ای برابر Timeout محدودشده به بازه ۱۰ تا ۱۵ ثانیه دارند. بنابراین Timeout کوچک‌تر از ۱۰ به معنی توقف تست سرعت در همان زمان نیست.

### TLS fragmentation — فرگمنت

| گزینه / کلید | کارکرد و راهنمای تنظیم |
|---|---|
| Enabled / `fragment.enabled` | قابلیت فرگمنت را فعال می‌کند، به شرط اینکه Mode خاموش نباشد. پیش‌فرض جدید خاموش است تا لینک بدون تغییر آزمایش شود. |
| Mode / `fragment.mode` | `off`: بدون فرگمنت؛ `manual`: مقادیر دستی؛ `auto`: قبل از اسکن پراکسی بهینه‌سازی اجرا می‌شود. تست مستقل کانفیگ بهینه‌سازی خودکار اجرا نمی‌کند؛ اگر فرگمنت روشن باشد، مقادیر دستی فعلی را به کار می‌گیرد. |
| Packets / `fragment.packets` | بخش‌هایی که Xray خرد می‌کند؛ مانند `tlshello` یا بازه `1-3`. عدد رنج آی‌پی نیست. |
| Manual → Length / `manual.length` | اندازه هر قطعه بر حسب بایت؛ مثلاً `10-20` یعنی اندازه‌های در این بازه. قطعه خیلی کوچک می‌تواند اتصال را بسیار کند کند. |
| Manual → Interval / `manual.interval` | فاصله میان قطعات بر حسب ms؛ مثلاً `10-20`. فاصله زیاد زمان برقراری اتصال را بالا می‌برد و ممکن است نیاز به Timeout بیشتر داشته باشد. |
| Auto → Length range → Min/Max | کمینه و بیشینه اندازه قطعاتی که بهینه‌ساز جست‌وجو می‌کند؛ باید مثبت و به ترتیب صعودی باشند. |
| Auto → Interval range → Min/Max | کمینه و بیشینه فاصله میان قطعات در جست‌وجوی خودکار؛ باید مثبت و به ترتیب صعودی باشند. |
| Auto → Max tests / `maxTests` | حداکثر تلاش هر ناحیهٔ جست‌وجو، نه سقف کل تمام آزمایش‌ها. بهینه‌ساز چند ناحیه مانند `tlshello`، `1-3` و `1-5` را بررسی می‌کند. |
| Auto → Success threshold / `successThreshold` | هدف توقف زودهنگام جست‌وجو در بازه ۰ تا ۱: تعداد موفقیت هدف برابر بخش صحیحِ Max tests × این مقدار، با حداقل ۳ است. این گزینه شرط پذیرش نهایی بر پایه درصد نیست؛ حتی یک نتیجه موفق هم می‌تواند بهترین نتیجه برگردانده شود. صفر از پیش‌فرض بهینه‌ساز استفاده می‌کند. |
| Auto → Test IP / `testIP` | مقصد آزمایش بهینه‌ساز؛ اگر خالی باشد در اسکن از اولین هدف و در اجرای مستقل از آدرس سرور استفاده می‌شود. برای Reality، آدرس سرور/هدف معتبر اتصال اهمیت دارد. |

دکمه **Optimize fragments** جست‌وجو را مستقل اجرا می‌کند و با فشردن دوباره متوقف می‌شود. پس از موفقیت، نتیجه در مقادیر دستی اعمال می‌شود. در حالت `auto` اگر جست‌وجو ناموفق شود، اسکن با مقادیر دستی ادامه می‌یابد و موضوع در گزارش ثبت می‌شود. فرگمنت تضمین عبور از محدودیت شبکه نیست؛ برای مقایسه با کلاینت دیگر باید تنظیم یکسان باشد.

### Output & automatic saving — خروجی

| گزینه / کلید | کارکرد و راهنمای تنظیم |
|---|---|
| Format / `output.format` | فرمت ذخیره خودکار `csv` یا `json`. برای بررسی همه جزئیات و خطاهای پروتکل، JSON مناسب‌تر است؛ CSV بومی برنامه هم وضعیت، اتصال و علت رد را نگه می‌دارد. |
| Directory / `output.directory` | پوشه نتایج؛ مسیر نسبی مانند `results` زیر پوشه داده برنامه قرار می‌گیرد. مسیر مطلق می‌تواند خارج از آن باشد. تغییر این گزینه فایل‌های قبلی را جابه‌جا نمی‌کند؛ تاریخچه پوشه انتخاب‌شده فعلی را نشان می‌دهد. |
| Save intermediate results / `saveIntermediateResults` | هنگام اجرا هر حدود ۵ تا ۶۰ ثانیه، متناسب با تعداد نتایج، نسخه میانی را در همان فایل اسکن ذخیره می‌کند. خاموش‌کردن آن ذخیره نهایی/نتایج جزئی هنگام توقف عادی را خاموش نمی‌کند. |

### Xray & multiplexing — هسته و Mux

| گزینه / کلید | کارکرد و راهنمای تنظیم |
|---|---|
| Log level / `xray.logLevel` | سطح پیام‌های هسته: `none`، `error`، `warning`، `info` یا `debug`. با گزینه ذخیره کانفیگ دیباگ فرق دارد؛ سطح زیاد جزئیات بیشتری تولید می‌کند. |
| Mux → Enabled / `mux.enabled` | چند جریان را روی اتصال مشترک حمل می‌کند. فقط اگر سرور و نوع اتصال سازگارند فعال کنید؛ برای مقایسه دقیق با لینک خام خاموش باشد. |
| Mux → Concurrency / `mux.concurrency` | تعداد جریان‌های هم‌زمان داخل یک اتصال Mux. وقتی Mux روشن باشد و مقدار مثبت نباشد، برنامه مقدار ۸ می‌گذارد. این گزینه با Threads اسکن فرق دارد. |
| Mux → Xudp concurrency / `mux.xudpConcurrency` | هم‌زمانی بخش XUDP در Mux، مربوط به ترافیک UDP. پیش‌فرض ۴؛ تست وب برنامه عمدتاً TCP است. |
| Mux → Xudp proxy UDP443 / `mux.xudpProxyUDP443` | رفتار XUDP برای UDP پورت ۴۴۳: `reject` رد، `allow` اجازه و `skip` عبور بدون Mux طبق رفتار هسته. پیش‌فرض `reject`. مسیر تست‌های HTTP/HTTPS برنامه را به‌تنهایی فعال/غیرفعال نمی‌کند. |

### Appearance و Debug & saving — ظاهر و نگهداری

| گزینه | کارکرد و راهنمای تنظیم |
|---|---|
| Theme | تم روشن، تیره یا مطابق سیستم؛ روی موتور اتصال اثر ندارد. |
| Language | فارسی/انگلیسی؛ هنگام اسکن باید ابتدا کار را متوقف کنید. |
| Save Xray debug config | اولین کانفیگ تولیدشدهٔ اسکن را در `first_config.jsonc` ذخیره می‌کند و اطلاعات تشخیصی بیشتری می‌دهد. این فایل ممکن است UUID و اطلاعات خصوصی داشته باشد؛ عمومی منتشرش نکنید. |
| Save settings | ذخیره فوری تنظیمات در پوشه داده کاربر؛ تغییرات معتبر معمولاً خودکار هم ذخیره می‌شوند. ورودی عددی نامعتبر ذخیره نمی‌شود تا اصلاح شود. |
| Reset | ابتدا انتخاب میان «فقط تنظیمات» و «تمام داده‌های برنامه» و سپس تأیید حذف را نشان می‌دهد. برای پاک‌کردن یک کانفیگ یا اهداف، از ریست همان بخش استفاده کنید. |
